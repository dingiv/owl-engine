# 2026-10-29 Qwen3.8-27B-pi-FP8 → AWQ INT4

## 结果

| 项 | 值 |
|---|---|
| 源 | `models/bytkim/Qwen3.8-27B-pi-FP8`（33G，FP8 blockwise 128×128） |
| 输出 | `models/bytkim/Qwen3.8-27B-pi-AWQ-INT4`（19G） |
| 方案 | compressed-tensors pack-quantized，g32-asym，400 个 Linear |
| 量化 | 271.5s（4m31s）；load 32.5s / quantize 210.4s / save 28.6s |
| 峰值 | 13.57 GiB（主卡；激活在第二张 3090） |
| 硬件 | 2×3090 Ti：主卡 `cuda:0`，`seq_offload=cuda:1` |
| 后处理 | `visual/embed` 的 FP8 反量化成 BF16；MTP 关闭（源 MTP 是 FP8，未拷） |
| 验证 | vLLM 512 ctx：`17*23` → `391`；owl 32k：`391` |

## 为什么看起来“只用 6G”

27B 的 33GB FP8 权重在 **CPU**，GPU 上只有：

- 主卡：当前 2 层 decoder subgraph + AWQ workspace（约 6.5G）；
- 第二张卡：`seq_offload=cuda:1` 的中间激活（约 1.6G）。

量化阶段主卡 GPU util 96%、约 300W；**算力是满的**，显存低是因为
sequential pipeline 一次只物化一个子图。前 ~1.5 分钟是 CPU FX tracing /
加载，GPU 空闲；之后才进入逐层量化。

## 源码判据

- `llmcompressor/pipelines/sequential/pipeline.py`
  - `onload_device = get_main_device()`：主卡；
  - `for subgraph_index, subgraph in enumerate(subgraphs)`：严格串行；
  - `subgraph_onload_modules(...)`：一次只 onload 一个子图；
  - 没有 layer-parallel scheduler。
- `llmcompressor/modifiers/transform/awq/base.py`
  - `_apply_smoothing()` 逐 mapping；
  - `_compute_best_scale()` 每层 grid search；
  - `_run_samples()` 重放父层输入；
  - 因此每层是一个串行的小 GEMM/量化任务。
- `DatasetArguments.sequential_offload_device` docstring：
  - 明确写的是 **intermediate activations**；
  - 多卡推荐 `cuda:1`，不是权重 offload。
- `compressed_tensors/offload/module.py`
  - `offload_module(module, onload_device, offload_device)` 支持权重
    卸到另一张卡；
  - 但 `SequentialPipeline` 只按主卡 onload，不暴露“层→卡”的 pool。
- `llmcompressor/entrypoints/oneshot.py`
  - `layerwise_decompression=True`：FP8 只在当前子图上解成 BF16；
  - 不会生成 54GB dense 中间目录。

## 为什么没走四卡

- 4 卡 DDP 数据并行 AWQ 实测：模型/数据分区正常，65 层跑完，但 finalize
  的 NCCL all-reduce 600s 超时；未跑通。
- 4 卡 `device_map=auto` + sequential 会 OOM（整模型先上卡）。
- 4 卡正确用途仍是并行跑多个任务；单模型 27B 用双卡 `cuda:1` 足够。

## 复现

```bash
CUDA_VISIBLE_DEVICES=1,2 python scripts/convert_pi27b_awq.py \
  --source models/bytkim/Qwen3.8-27B-pi-FP8 \
  --output models/bytkim/Qwen3.8-27B-pi-AWQ-INT4 \
  --device cuda:0 --seq-offload cuda:1 \
  --samples 128 --seq-len 2048 --batch-size 8 --n-grid 10 \
  --targets-per-subgraph 2 --cpu-memory 80GB
```

输出后需要去掉 MTP 声明，并把 visual/embed 的 FP8 反量化到 BF16；
本次已用 `FP8BlockDequantizer` 完成，产物 19G。

## 质量门（2026-10-29 完成）

### 口径

- **题集**：GSM8K test 前 200 题（本地
  `repos/vllm-ampere-optimized/benchmarks/gsm8k.jsonl`），greedy
  （`temperature=0`）、`enable_thinking=false`、统一 "Final answer:" 指令；
- **needle 16k**：暗号 `K7-ZEBRA-4713` 埋在 ~16.2k prompt 的 head / mid / tail，
  要求原样输出；
- **std**：`packages/llm_speedtest --flavor std`（512/1024/2048/4096/8192 ×
  3 轮，输出 256，单并发）；
- 工具：`scripts/quality_gate.py`（新）+ `scripts/compare_quality.py`（配对
  McNemar）；
- **参考臂 = FP8 源**：本地没有 27B BF16。vLLM 在 sm86 上对 blockwise FP8
  走 **Marlin W8A16**（block scale 折进权重、激活 bf16），即“官方 FP8
  权重 + 比官方 dynamic-FP8 更宽的激活精度”——对 AWQ 是**保守**基线。
  源模型卡未发布 GSM8K，无法用官方分对照。

### 结果

| 轮次 | 引擎 | 硬件 | c | max_tokens | GSM8K 200 | needle 16k | 撞顶 |
|---|---|---|---:|---:|---:|---|---:|
| AWQ owl | owl | 1×3090 Ti | 1 | 768 | 95.0%（190） | 3/3 | 8 |
| FP8 vLLM | vLLM TP2 | 2×3090 Ti | 8 | 768 | 96.5%（193） | 3/3 | 6 |
| AWQ vLLM | vLLM TP2 | 2×3090 Ti | 8 | 1536 | 96.5%（193） | 3/3 | 4 |
| FP8 vLLM | vLLM TP2 | 2×3090 Ti | 8 | 1536 | **97.0%（194）** | 3/3 | 6 |
| AWQ owl | owl | 1×3090 Ti | 1 | 1536 | **96.5%（193）** | — | 1 |

配对检验：

| 对比 | Δ | 配对格 | McNemar |
|---|---:|---|---:|
| 768：owl AWQ vs vLLM FP8 | -1.5pp | 189 / 1 / 4 / 6 | p=0.375 |
| 1536：owl AWQ vs vLLM FP8 | **-0.5pp** | 192 / 1 / 2 / 5 | **p=1.000** |
| 1536：owl AWQ vs vLLM AWQ | **0.0pp** | 193 / 0 / 0 / 7 | p=1.000 |

> 配对格 = 都对 / 仅前者对 / 仅后者对 / 都错。

### 判定

1. **GSM8K 通过**。同预算 1536：AWQ 96.5% vs FP8 97.0%，差 -0.5pp 在
   -1pp 门内；McNemar p=1.00，统计不可分。更强的一条：**owl 与 vLLM 跑
   同一 AWQ 产物，200 题逐题结果完全一致（0 翻转）**——跨引擎差异被排除，
   剩余 1 个 AWQ 独对、2 个 FP8 独对属采样/数值噪声。
2. **needle 16k 通过**：head/mid/tail 全中（prompt 16233/16234/16233 tok），
   owl 13.0-13.4s、vLLM 9.2-9.3s。
3. **std 15/15 通过**（owl 单卡）：prefill avg 1142.6 t/s（895.7-1311.0），
   decode avg 22.5 t/s（22.3-22.7），TTFT avg 2593ms（563-6335）。

### 两个测量注意

> 完整的“为什么慢 / 怎么变快 / 使用注意事项”见
> `docs/bench/2026-10-29-speed-and-usage-notes.md`。

- **768 档会误伤**：pi 是 agent 特调、输出很长（均值 360-382 tok），768
  下 3-4% 的题被截断，且 AWQ/FP8 截断数不同（8 vs 6）→ 出现 -1.5pp 的
  假性差距。质量门用 **1536**；GSM8K 类评测建议 ≥1536。
- **std 的 decode 22.5 t/s 不是带宽上限**：ITL 恒 44.4-45ms（与 ctx 无关），
  而 greedy 路径（GSM8K）实测 ~45 t/s（19G 权重 / 22ms ≈ 863GB/s，已贴
  3090Ti 带宽墙）。差异来自 `temp=1/top_p=0.1` 的采样路径（每 token 多
  ~22ms），不是量化或长上下文问题。
