## §0 一句话

把当前 ctx 的 fp8 K/V 每层**一次**反量化到 f16 shadow，再走 FI f16
prefill 臂；3080 TP2 实测：

- attention 核 **1.265×**（100k / T=2048，含 dequant）；
- 端到端 prefill **+3~5% @29k、+8~9% @100k**；
- 100k needle 检索通过；
- **greedy 不保证逐字一致**（f16 vs fp8 在近 tie 处分叉），故默认关。

## §1 施工内容

### 1.1 数据面

```text
生产池：fp8 e4m3, kNHD, [nb, page, hkv, hd]
  │  owl_fi_dequant_fp8_to_f16（每层一次，按 indices 取物理页）
  ▼
shadow：f16, dense 逻辑页 [ctx_pages, page, hkv, hd]
  │  identity 页表 + [0, nb]
  ▼
FI f16 prefill 臂（只用于 T>=64；decode/verify 仍走 fp8）
```

- `owl_kv_fp8_to_f16_kernel`：4 个 e4m3 → 4 个 half，K/V 同一套；
- `owl_fi_prefill_plan2(..., kv_bytes)`：显式 f16 plan，不读 env；
- `PlanKey` 增加 `kv_bytes`：fp8/f16 plan 不互吃；
- `FiRuntime::ensure_shadow`：K/V scratch + identity 表。

### 1.2 容量：boot 期固定 cap（本轮修的 OOM）

第一版按 **当前 ctx** 增长。100k 时池已接近满，shadow 从 59MB 扩到
68MB 被硬预算拒发：

```text
PoolExhausted: vram-hard-budget(驱动 free − reserve) 需 71303168B 余 39583744B
```

修法：

- boot 期 `set_prefill_shadow_cap(runtime.max_seq)`；
- 首层 FI 调用一次性按 cap 预留（3080 TP2：262144 tok × 2KiB = **512MiB/rank**）；
- 后续 ctx 增长不再分配；`ctx_pages > cap_pages` 结构化拒；
- 首次分配日志：

```text
[kernels] FI prefill shadow 预留: 512 MiB/rank(cap=262144 tok, 8192 页, page=32, hkv=2, hd=256)
```

修复后 100k 连续跑通，不再在池压力峰值扩容。

### 1.3 开关（默认关，仅 fp8 主池）

```toml
[kernel]
prefill_shadow = false   # 实验；默认关；仅 [pool] kv_fp8=true 可用
```

用户裁决（2026-10-26）：

- **默认关闭**，不随 3080 档转正；
- 这是 **FP8→F16** 的 prefill-only 影子，**只允许 fp8 主 KV 池**；
- `prefill_shadow=true` + `pool.kv_fp8=false` = `validate` **拒启**，
  不允许 f16 主池静默走一个无意义的影子；
- 运行期 `shadow` 条件再加 `call.fp8kv` 双保险。

运行期：

```bash
./target/release/server -p profiles/qwen38_27b-3080_tp2.toml \
  --set kernel.prefill_shadow=true
```

`decode_arm/verify_arm` 不动；`t < 64` 的尾块仍走 fp8。

## §2 数值审计：0.25 不是 CTA64 bug

上一轮交接把下面这组当成 f16 CTA64 数值错误：

```text
T=4  max|Δ| = 0.25
T=8  max|Δ| = 0.25
```

本轮定位：**这是输出幅度 ~448 时的 1 个 f16 ULP**（448 附近 ULP=0.25）。
绝对门 `2e-3` 对 f16 输出没有意义。

改用相对门 + torch f32 参考：

| 形状 | 臂 | vs torch f32 `rel_l2` | vs torch f32 `rel_max` |
|---|---|---|---:|---:|
| T=64 / ctx32k | fp8 | 8.95e-5 | 6.84e-4 |
| T=64 / ctx32k | f16 shadow | 1.45e-4 | 2.21e-3 |
| T=64 / ctx100k | fp8 | 1.15e-4 | 1.68e-3 |
| T=64 / ctx100k | f16 shadow | 3.15e-4 | 5.87e-3 |

短形状 T=8/ctx256 对 host16：

```text
fp8  rel_l2 = 4.374e-5
f16  rel_l2 = 4.317e-5   # 与 fp8 同级
```

结论：

- f16 不是坏值，**没有 CTA64 越界/错行**；
- f16 比 fp8 精度低约 1.5~2.7×（不同 tile/累加顺序），但仍在
  `rel_l2 ≤ 3.2e-4` 量级；
- 探针门已改为 `rel_l2 < 2e-3 && rel_max < 3e-2`，不再用绝对 2e-3。

## §3 3080 性能

### 3.1 核级（单 3080，T=2048，ctx=100k）

```text
fp8              = 118.003 ms
f16 shadow(+dq)  =  93.192 ms   speedup = 1.266×
dequant          =   0.926 ms   （占 1%）
```

T=807 同 ctx：49.454 → 39.105 ms，**1.265×**。

### 3.2 端到端（3080 TP2，prefill 日志口径）

**spec off**（`spec.depth=0`，排除投机干扰）：

| 场景 | fp8 | f16 shadow | 变化 |
|---|---:|---:|---:|
| 29k 冷 prefill | 18.689 s / 1572.3 t/s | 18.103 s / 1623.2 t/s | **+3.2%** |
| 100k（29k cached，73k 新） | 64.018 s / 1141.4 t/s | 58.965 s / 1239.2 t/s | **+8.6%** |

**spec d7**（生产档）：

| 场景 | fp8 | f16 shadow | 变化 |
|---|---:|---:|---:|
| 29k 冷 prefill | 19.336 s / 1518.0 t/s | 18.451 s / 1592.5 t/s | **+4.8%** |
| 100k（29k cached，73k 新） | 65.304 s / 1118.9 t/s | 59.793 s / 1222.0 t/s | **+9.2%** |
| 102.5k 冷 prefill | 84.284 s / 1216.3 t/s | 79.332 s / 1291.8 t/s | **+6.2%** |

100k 冷 run 有轻微顺序/时钟偏差（shadow 是第三发），以 29k cached
那一组为主判据。

### 3.3 为什么端到端不是 1.26×

attention 只占 prefill 的一部分；100k 时约 30%，29k 时约 12%。
1.26× attention 对应端到端 +3~9%，与实测一致。

## §4 质量

### 4.1 100k needle 检索

在 100k 随机词流中间插入：

```text
The secret passcode is XQ-7391.
```

末尾问 passcode。两臂均正确：

```text
fp8  : XQ-7391
f16  : XQ-7391
```

### 4.2 greedy 不保证逐字一致

同一个 29k “最后五个词” prompt，96 tok 内：

- fp8 先猜 `"...dahlia tau mu"`，随后开始怀疑；
- f16 直接引到完整后缀
  `"...juniper crimson dahlia tau mu"`，并准备回答。

这是近 tie 分叉，不是 f16 明显更差；本轮 100k needle 两臂都过。
但 **不能把 f16 shadow 当作 bitwise parity**。默认关，等质量签收。
