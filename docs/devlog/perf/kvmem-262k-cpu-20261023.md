# KVMem 262K prefill CPU 调度层实测（2026-10-23）

> 档：`qwen38_27b-3090-gguf-kvmem-262k.toml`
> Qwen3.8-27B Q4_K_M，单 3090 Ti，FP8 KV，80K execution view，
> 设备池 85568 tok，host 11264 MiB，`recall_every=4`，`query_replay=true`。

## 1. 实测（260K prompt）

```text
prompt=260018 tok / completion=1 tok
WALL=355.5 s
```

`[kvmem-prof]`：

```text
boundaries=507 full=127 cheap=380
index=87573.5ms  qface=31527.1ms  score=2831.9ms
select=4460.9ms  view=1386.3ms  reconcile=30837.4ms
total=41468.6ms
```

（`total` 不含 qface；qface 在 `prefill_chunk_enqueue` 的 Q 回读段。）

## 2. 这一刀做了什么

`recall_every > 1` 的廉价边界（380/507）**不再采 Q、不再做 query 面**
（`q_needed=false` → `CoveragePending::cheap`）。只有完整召回/诊断边界
（127）才走 Q D2H + 逆 RoPE + `score_blocks`。

对照：r16 档（Q 未跳）qface **124318ms**；本档 qface **31527ms**，
降约 **93s**。

## 3. 但墙钟没有相应下降：新主项是 index / reconcile

| 相位 | 本档 | 说明 |
|---|---:|---|
| `index` | **87.6s** | Mean-K 索引 D2H + host 逆 RoPE（8K 块 ≈ 8GB K 回读） |
| `qface` | 31.5s | 127 个完整召回 × W=64 行 |
| `reconcile` | **30.8s** | 廉价边界冻结集 + 尾部增长带来的下沉/回灌 |
| `score` | 2.8s | `recall_every=4` 后已不是主项 |
| `select` | 4.5s | 127 次 8192 块选择 |

⇒ 只跳 Q 不够。262K 的 CPU/PCIe 主项已经变成 **Mean-K 索引采集**和
**驻留调和**。

## 4. 262K 质量：80K view 仍不够（负结果）

coherent needle，code 在 token ~28.9K（逻辑块 902）：

- final view=2560 页；
- `bids` 含 block 902；
- 输出 **`**`**，未答出 `BLUEBIRD-42`。

⇒ 262K 下 80K view（≈30% 覆盖）仍可能“选中针块但模型用不上”；
90K/80K view 可以，262K 不行。下一步要么更大 view，要么 compact
position/re-RoPE，不能只靠 query replay。

## 5. CPU 调度层优化清单（按收益）

1. **Mean-K 的 GPU 侧增量归约**（论文 §5.3）
   - 当前 `collect_index_for_blocks`：每块 16 层 K 页 D2H（≈1MB/块），
     262K ≈8GB，host 逆 RoPE/累加。
   - 应改成 prefill 核内块边界归约（`MeanKCollector` 上 GPU），只回读
     f16 索引（每块 32KB），把 87s 的主项消掉。
2. **廉价边界不采索引/不同步**  
   索引只服务下一完整召回；廉价边界不 score ⇒ 可把索引采集也按
   `recall_every` 批量/延后（最终召回前补齐），减少 D2H 与 host 抢占。
3. **reconcile 批量化/异步化**
   - 当前每个廉价边界下沉/回灌；`reconcile=30.8s`。
   - 用论文的 proactive stage-out（chunk n 完成即异步下沉，与 chunk n+1
     重叠）+ 更大的批，把同步等待移出 prefill 关键路径。
4. **step-level 调度**
   - 最终只剩约 1 次完整召回/step；本轮 127 次是 `recall_every=4` 的折中。
   - 步级化后 Q/score/select 都再降一个量级；但必须同时解决视图尾部
     增长（池下限已改成 `workspace + recall_every × chunk`）。
5. **GPU-tiled scoring**（1M 规模再上；当前 score 2.8s 不是瓶颈）。
6. `-C target-cpu=native` 对 host 逆 RoPE/打分有 ~2×（文档旧读数）。

## 6. 已修的 boot 约束

`recall_every > 1` 时，召回点之间视图尾部最多长 `recall_every` 个 chunk；
池下限从 `workspace + chunk` 改为：

```text
workspace_pages + recall_every × chunk_pages
```

262K r16 档需要 `2560 + 256 = 2816` 页，> 2674 页池 ⇒ 本应 boot 拒；
现在会响亮拒，不再跑到 84K 才 Exhausted。
