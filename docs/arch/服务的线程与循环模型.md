# 服务的线程与循环模型(设计正本)

> 版本 v1.0(2026-11-03)。**读它的场合**:怀疑"某个东西没停下来"、要加新的后台
> 工作、要动关停/取消语义、或者想不通"为什么引擎不能立即中断"。
>
> 一句话:**HTTP 面是多任务的、引擎是单任务步进的、设备面是每卡一条命令线程的** ——
> 三层的"时间粒度"完全不同,所有跨层协作都必须落在**步边界**上。

---

## 一、线程清单(谁建 / 跑什么 / 怎么收摊)

| # | 线程 | 谁建 | 跑什么 | 生命周期 | 为什么必须独立 |
|---|---|---|---|---|---|
| 1 | **main + tokio 多线程 runtime**(workers = `min(nproc, 16)`) | `#[tokio::main]` | accept 循环、每连接任务(`serve`)、每请求 handler(含整段 SSE 写)、信号任务 | 进程 | HTTP 面是**并发**的:一个慢客户端只需占住它自己的任务 |
| 2 | **`engine-executor`**(std 线程,栈 32 MiB,自带 `current_thread` runtime) | `main.rs` `thread::Builder` | `executor_main`:建设备句柄 → 装载权重 → `executor::run_executor` **泵循环** | 进程(先于 HTTP 面就绪,后于它收摊) | `RunningEngine` **非 Send**(持有 CUDA 侧句柄/图/池),必须在**同一线程**建→用→销毁;且泵循环不能被 HTTP 任务抢占 |
| 3 | 引擎线程内的 `current_thread` runtime | `executor_main` 里 `Builder::new_current_thread` | 驱动 `RunningEngine` 的 async 面(命令发射/等待 ack) | 引擎线程 | 引擎内部的 await 只需**单线程调度**:真并发在设备 server 线程里 |
| 4 | **设备 server 线程**(TP2 = 每 rank 一条,共 2) | `GpuClient::new`(`crates/backends/cuda/src/gpu_client.rs`) | `GpuServer::run()`:`loop { rx.recv() → 执行 CUDA → ack }` —— **CUDA context 在这里** | 命令通道关闭(全部客户端离场)⇒ 设备栅栏 ⇒ 退出 | CUDA context/stream 必须**单线程串行**持有:这是"同步隔离"(A3)的落点 |
| 5 | **派发线程**(每 rank 一条,`owl-gpu-<sel>-dispatch`) | `GpuServer::run` 内 | 排空 host 回调(`Finish`):host 回调只投递,真 CUDA 收尾在此 | 通道关闭后自然收尾 | CUDA host 回调里**不许**做 CUDA 调用(会死锁)⇒ 必须转发到普通线程 |
| 6 | TP2 装载期的两个 `current_thread` runtime | `executor_main`(`load_shard` rank0/rank1) | 逐 rank 驱动装载 future(**顺序**,同一线程) | 装载结束即 drop | 装载链是 async 的,但 rank 之间必须严格排序(共享设备面) |

### 实测清单(2026-11-03,48 核机器 / 双 3080 TP2 / `profiles/qwen38_27b-3080_tp2.toml`)

`/proc/<pid>/task/*/comm` 逐线程统计(名字即证据):

```
52  owl-dev-o3-srv      ① 设备 server 线程(rank0)+ 装载期在它名下创建的 CUDA/NCCL 线程
16  tokio-rt-worker     main 的多线程 runtime:**worker = min(nproc, MAX_HTTP_WORKERS=16) = 16**
 3  owl-dev-o4-srv      ② 设备 server 线程(rank1)+ 同类
 2  cuda-EvtHandlr      驱动内部
 1  server              main
 1  owl-dev-o3-dsp      派发线程(rank0)
 1  owl-dev-o4-dsp      派发线程(rank1)
 1  engine-executor     **引擎线程(唯一背 `RunningEngine` 的那条)**
```

三条要点:

1. **tokio worker = `min(nproc, 16)`**(2026-11-03 用户裁决):tokio 缺省吃
   `available_parallelism()`(本机 48 核 ⇒ 48 条 worker),而 HTTP 面是**纯 I/O 等待**
   (写 socket / 等引擎事件),真算力在 `engine-executor` 与设备 server 线程里 ⇒ 48 条
   worker 只多占栈与调度。现在显式 `worker_threads(min(nproc, MAX_HTTP_WORKERS))`
   (`MAX_HTTP_WORKERS = 16`,boot 行会打印实际值:`worker=16(nproc=48, 上限 16)`)。
2. **每连接/每请求不是线程**:`serve()` 与 `chat()` 都是 **tokio 任务**(跑在 worker
   上),一个连接一个任务、连接内请求**串行**(`serve` 会 await 整段流式应答)。
3. 线程名一律 **≤15 字符**(`comm` 被内核截断):`owl-dev-{o3|u7d}-srv` / `-dsp`
   成对;此前设备 server 线程**没有名字**,新线程 `comm` 继承创建者 ⇒ 一堆线程
   都显示成 `engine-executor`/`owl-engine`,排障时分不清层面(2026-11-03 修)。

**没有**的东西(见 §七):per-session 任务、引擎内自旋循环、后台定时器线程。

## 二、一次流式请求的完整路径

```
                          ┌──────────────────── main(tokio 多线程)────────────────────┐
 TCP ── accept ──▶ serve() ── read_request(keep-alive ≤30s/≤1024 请求)
                     │
                     └─ handle() ─▶ openai::chat()
                                      │ ① session 闸(同会话串行;跨会话并行)
                                      │ ② 并发 permit(全局位)
                                      │ ③ EngineReq::Chat ──tx(mpsc 64)──▶ [owl-engine 线程]
                                      │                                    │
                                      │ ④ 等首个 SinkEvent(Accepted)◀──sink(每 turn 一条)─┘
                                      │ ⑤ 写 SSE 头(chunked)
                                      ▼
                          ┌── 事件循环(select;4 路)──────────────────────┐
                          │  a) SinkEvent::Turn(Token{delta})  → 写一帧 SSE + flush
                          │  b) SinkEvent::Turn(Prefill{..})   → 只改 usage(不写字节!)
                          │  c) SinkEvent::Session{cached}     → 只改 usage
                          │  d) SinkEvent::Turn(Completed/Failed) → 尾帧 + sse_end
                          │  e) **读半就绪**(`peek` 非消费)    → FIN/RST ⇒ 断流(事件源①)
                          │  f) 保活到点(keepalive_ms)        → 写 SSE 注释帧(断流源②)
                          │  g) 排队超时(queue_wait_ms)        → 429 + 弃置
                          └──────────────────────────────────────────────┘

 [engine-executor 线程]  run_executor 泵循环
      loop {
        ① rx.try_recv 排空(Abort / 新请求 / 查询)  ← 步边界
        ② 停服? 有人要吗?  ← **步边界的两项状态检查**(§五)
        ③ pump().await   = 一拍:一个 prefill chunk / 一个 decode 步 / 一个 spec 轮
        ④ dispatch(ev)   = 投进该 turn 的 sink(满则 await = 背压)
      }

 [设备 server 线程]  loop { rx.recv() → 执行这条 CUDA 命令 → ack }
```

**粒度对照**:一次 SSE 帧 = 一个 token;一拍引擎 = 一个 chunk 或一个 token;
一条设备命令 = 一次内核发射/一次 D2H。**跨层取消只能落在"拍"的边界上。**

## 三、循环清单(退出条件是最重要的字段)

| 循环 | 位置 | 一项工作的粒度 | 退出条件 |
|---|---|---|---|
| accept | `main.rs` | 一次 `accept()` | **stop watch**(SIGTERM)⇒ break;否则永不退出 |
| 连接循环 | `main.rs::serve` | 一个 HTTP 请求(**含整段流式应答**) | 对端关闭 / `Connection: close` / 1024 请求 / 空闲 30 s / IO 错 |
| 请求事件循环 | `openai.rs::chat` | 一个 `SinkEvent`(或保活到点/排队超时) | 终态事件 / 写失败(⇒ `sink_rx.close()` + `abort_turn`) |
| engine executor 泵循环 | `executor.rs::run_executor` | **一拍** = 1 chunk / 1 token / 1 spec 轮 | stop watch / `EngineReq` 通道关 / 致命错(`is_fatal`)⇒ 返回 `ExitReason` |
| 设备 server | `cuda/server/mod.rs::run` | 一条 `Command` | 通道关闭(所有客户端句柄 drop) |
| 派发线程 | `cuda/server/mod.rs::run` | 一个 `Finish` 回调 | 通道关闭 |
| 引擎内部 | — **无循环** | — | — |

## 四、所有权与同步纪律(违反即返工)

1. **`RunningEngine` 只在 `owl-engine` 线程里存在**(非 Send)。HTTP 面**永远**只经
   `EngineReq` 通道说话:没有共享状态、没有锁、没有 `Arc<Mutex<engine>>`。
2. **CUDA context 只在设备 server 线程里摸**。引擎线程发命令、等 ack;`Mirror2`
   把同一动作投给两个 rank 的 server 并发执行。这就是"**同步隔离**":一卡慢不拖
   另一卡的 host 面。
3. **`&mut` 独占一个拍**:`pump()` 期间引擎把整拍做完才返回,期间不接新请求
   ⇒ **提交/取消/查询都发生在两拍之间**(`executor.rs` 泵间 `try_recv`)。
4. **可失败逻辑一律 `Result` 上抛**:泵循环收到 `Err` ⇒ ① 打日志 ② 丢该 turn
   (`abandon_turn`,引擎错语义 = **不发布**缓存)③ 致命者返回 `ExitReason::Fatal`。
   `catch_unwind` 只兜**设计外** panic(同一条收摊路径,退出码 70)。
5. **慢消费者会停住引擎**(已知且刻意的背压):sink 容量 64,`deliver` 用
   `send().await` ⇒ handler 写不快 ⇒ executor 阻塞 ⇒ 整台引擎停拍。单槽档(3080/3090
   生产档)下这等于**一个慢客户端拖住所有会话**。要改就得给 sink 加"丢弃+重同步"
   语义(未做;先记录在案)。

### 为什么 `engine-executor` 是 `std::thread` 而不是 `tokio::spawn_blocking`

三条,任一条都足以否掉 `spawn_blocking`:

1. **`spawn_blocking` 的闭包必须 `Send`**;而 `RunningEngine` **非 Send**(持有
   CUDA 句柄/图/池,`cudarc` 类型未标 `Send`),且它的生命周期跨越无数 `await`
   ——"搬进阻塞线程池"这件事在类型层面就不成立。
2. **栈**:引擎线程要 32 MiB(`ENGINE_STACK_BYTES`;debug 档 27B+DFlash2 装载链
   实测在 2 MiB 缺省栈上 SIGABRT)。专用 `thread::Builder` 能显式给,阻塞线程池
   给不了"只给这一条"的语义。
3. **运行时隔离**:引擎线程要跑**自己的** `current_thread` runtime(它的 await
   只该服务引擎自己的命令往返),不能和 HTTP 面的 worker 抢调度、也不能让
   HTTP 的负载把泵循环的唤醒延迟拉高。

## 五、步边界上的两项状态检查(2026-11-03 立)

`run_executor` 在**每一拍之前**查两件事,命中就**不再推进**(不是"跑完再说"):

```rust
// ① 停服:watch(SIGTERM) 或 请求通道关闭
if *stop.borrow() || rx.is_closed() { return ExitReason::Normal; }
// ② 还有人要吗:本 turn 的 sink 是否已被接收方关闭
if let Some(t) = running.active_turn_id() {
    if sinks.get(&t).is_some_and(|s| s.is_closed()) { dropped = Some(t); }
}
// ③ 弃置(客户端取消语义:发布已写入前缀 + 中断补拍快照)
if let Some(t) = dropped.take() { drop_turn(running, &mut sinks, 0, Some(t)).await; }
```

为什么必须有这两项(而不是靠"投递失败"这种副作用):

- **prefill 阶段流上零写入**(`Prefill` 事件只改账本)⇒ 客户端 FIN 不会让任何写
  失败 ⇒ 旧实现只有"首个 token 写失败"才会察觉 ⇒ **整段 prefill 白跑**
  (实测:198495 tok 的 turn 断流后仍跑满);
- 每个连接任务都持有 `EngineReq` 发送端**克隆** ⇒ "通道关闭"在长流请求在场时
  **永远不会**发生 ⇒ 停服信号必须走独立的 `watch`(这就是"多事件源监听"的落点);
- 判据与相位无关:**prefill chunk 与 decode(含 spec 轮 / CUDA 图重放)一视同仁**
  —— 检查发生在**发射之前**,所以"放完一次图不再放第二次"是结构性成立的。

### 断流的三个事件源(互补,缺一不可)

| 源 | 手段 | 覆盖 | 延迟 |
|---|---|---|---|
| ① **读半 FIN/RST** | `TcpStream::peek`(**非消费**) | 客户端正常关闭 / 前端 abort / SDK close / RST | **瞬时**(FIN 到达即醒,不用先写) |
| ② **保活写失败** | `keepalive_ms` 周期写 SSE 注释帧 | **没有 FIN 的掉线**(拔网线 / NAT 超时 / 客户端僵死) | ≤ `keepalive_ms` + TCP 超时 |
| ③ **投递失败**(兜底) | `sink.send()` 返回 Err | handler 已退出但没走 `close()` 的边角 | 下一拍 |

**通知链(三源合一)**:

```
①读半FIN / ②保活失败 / ③投递失败
        │
        ├─ handler: sink_rx.close()          ← "我不再收了"(关闭态 = 通知)
        │           abort_turn(EngineReq::Abort) ← 显式指名取消(≤1 拍)
        ▼
   executor 泵循环 · 每拍之前
        ├─ *stop.borrow() / rx.is_closed()          ⇒ 停服
        └─ sinks[active_turn].is_closed()           ⇒ 本 turn 没人要了 ⇒ drop_turn
        ▼
   下一拍**不发射**(prefill chunk / decode / spec 轮一体适用)
```

即:**handler 不需要"通知引擎停止"这件事被特殊对待** —— 它只做两件平凡的事
(关接收端 + 发一条 Abort),引擎把"接收端关闭"当成**每拍必查的状态**。

## 六、关停:一条路径,三种原因,零 `process::exit`

```
SIGTERM/SIGINT ─┐
引擎致命错 ─────┼─▶ ExitReason ─▶ main:drop(listener) → drop(tx) → join(executor)
设计外 panic ───┘                                             │
                                                              ▼
                                             release_locks(全 rank) → return ExitCode
```

| 原因 | 触发 | 退出码 | 语义 |
|---|---|---|---|
| `Normal` | stop watch / `EngineReq` 通道关闭 | **0** | 运维停服:不再接新连接、当前拍做完即停、join 后释放卡锁 |
| `Fatal` | `ModelError::is_fatal`(显存硬预算 / 设备 server 关) | **1** | 引擎不可恢复;同一条收摊路径 |
| `Panic` | `catch_unwind` 兜到的设计外 panic | **70** | `EX_SOFTWARE`:supervisor 据此决定重启 |

**为什么不再 `process::exit`**(2026-11-03 用户裁决):
`exit` 跳过 Drop(卡锁/设备句柄全靠显式救)、跳过 `main` 尾部(收摊顺序失去保证)、
跳过 `atexit`。收摊必须**按顺序**发生:先停接新连接 → 再停引擎(它在自己的线程里
drop `RunningEngine`,设备/图/池必须在该线程销毁)→ 再 `join` → 再放锁 → 再返回。

## 七、刻意不做的事(以及为什么)

| 不做 | 原因 |
|---|---|
| **per-session 任务 / per-session 循环** | session 在引擎里**只是一行账**(`tokens/cached_len/block_table/chain/…`)。执行单位是 **turn**,`turns.queue` / `turns.active` 是扁平数组。造 per-session 任务 = 把"设备命令只由一个串行推进器发出"这条公理拆掉(A1/A3) |
| **引擎内 `tokio::select!` 监听多源** | 不需要:泵循环本身就是"步间检查多源"(`try_recv` + `stop.borrow()` + `sink.is_closed()`)。"select"只在 **handler** 里(等事件/保活/排队超时) |
| **chunk 内可中断** | 一拍的 CUDA 命令已按流序入队,唯一安全的中断点是**拍边界**。要更细就减 `prefill_chunk`(代价:每 chunk 固定宿主税 ≈250 ms,2048 是甜点) |
| **后台定时器线程** | 保活/排队超时都是 handler 内的 `tokio::time`(任务级,不占线程) |
| **共享引擎状态给 HTTP 面** | 读面一律走**快照单元**:`Telemetry`(executor 每拍写)、`DbgFace`(`OnceLock<Mutex<face>>`)。HTTP 侧零等待、零锁竞争 |

## 八、排障入口(日志 tag ↔ 线程)

| tag | 出自 | 看什么 |
|---|---|---|
| `[conn]` | main/连接任务 | accept 失败、断连、空闲超时 |
| `[chat]` | handler | 受理、保活帧写失败、指标行(`ttft/prefill/decode/cache`) |
| `[executor]` | 泵循环 | 停服/接收方已关闭、弃置 turn、泵错误 |
| `[prefix]` / `[snap]` | 引擎(engine-executor 线程) | 中断落账、中断补拍、复用面 |
| `[sched]` / `[spec-*]` | 引擎 | 拍耗时、投机降级/恢复 |
| `[boot]` | main | 就绪/收摊原因/卡锁释放 |
