## 一、一句话结论

> **接入一种新格式 ≈「3 个一次性架构点 + N 个加臂点 + 4 类门」。**

- **一次性架构点**(做完一次,后续格式几乎白拿):`PlanSource/PlanTable`(逐张量计划)、
  `SourceFacts`(源事实)、`KeyConvention::head_key`(第 4 类键)、`Model::new -> Result`;
- **加臂点**(每个格式各做一遍):起点族(容器/超参/词表/键约定/权重源)+ 装载开箱 +
  需要的层臂 + 解码头臂 + 内核族 + 引擎入口 + 服务档位;
- **门**:资源清单 / e2e / 交叉源对拍 / 源码卫生(I-4)/ 白名单两处锁。

**GGUF 的实际成本**(相对 W4A8 基线 `main@ae2f8ae`):

```text
既有文件 34 个:+1575 / −162 行
新增      ≈ 9.1k 行:formats/gguf/ 4393 · cu/gguf/ 2956 · kernels 域表 784 · 门/工具/档 ~1k
门         formats::gguf 29 · engine e2e 3 · op_tables 10 · no_runtime_compile 4 · ops_whitelist 2
```

**三种格式的"改动形状"对照(实测)**:

| 档位 | 起点族 | 是否动量化解码 | 是否动层语义 | 是否动服务面 |
|---|---|---|---|---|
| SafeTensors(F16 基线) | `safetensors/source.rs` | 否 | 否 | 否 |
| AWQ / compressed-tensors(W4A8/W4A16) | `awq/` `w4a16/` + marlin 重排 | 是(解包到 marlin 布局,一次性) | `Linear` 加臂 | 否(档位枚举 +1) |
| **GGUF(k-quant/IQ)** | `gguf/`(11 模块 4.4k 行) | **否**(dequant-in-kernel,压缩驻留) | **是**(六类布局变换 + 逐张量型) | **是**(单文件自给:词表/模板/rope) |

> **判别式**:先把上面三列答清楚,再决定工作量。
> GGUF 之所以最贵,**不是因为容器难解析**,而是后两列都打了勾。

## 二、分层改动面(A→G)

每行给「改什么 / 为什么 / GGUF 实证」。

### A. 架构面(**一次性**;若新格式提出新诉求才动)

| # | 落点 | 改什么 | 为什么 | GGUF 实证 |
|---|---|---|---|---|
| A1 | `module.rs` | **`PlanSource` / `PlanTable`**:`Uniform(QuantPlan)` 与 `Keyed{表, 键约定, 层号}` 两臂;`impl From<QuantPlan>` 让既有调用点零改动 | 量化型/精度可能是**逐张量**事实(27B 混 Q4_K 193 + Q8_0 288 + Q6_K 17 + F32 353;4B 同角色跨层不同型)⇒ 全局单值表达不了 | +189 行;40+ 既有调用点逐字未改 |
| A2 | `module.rs` | **`SourceFacts`**:源把什么烘焙进了数值/键面(norm `+1`、融合键可异型、v-head 列序) | 与 plan 正交,但消费者是同一批构造器 ⇒ 走**同一注入通道**,层构造签名不加路 | 3 条事实;GGUF 档 RmsNorm 用 `×w`、GDN 声明两 Linear、out_proj 挂列序表 |
| A3 | `module.rs` | **`KeyConvention::head_key`**(embed/layer/norm 之外的第 4 类键) | untied 头在各格式里名字不同(GGUF `output.weight` / HF `lm_head.weight`)⇒ 命名事实必须由约定答,不能硬编码 | 顺手删掉 `PlanTable::lm_head_key()`(= 同一事实的第二个出口) |
| A4 | `model.rs` | `Model::new -> Result` + 构造期**计划覆盖门** | 缺键/未移植型必须在**构造期**判死:计划定形 ⇒ 槽形状/显存账定形;静默落 F16 会让账在装载后才失真 | +97 行 |

**纪律**:新格式若**不**需要"逐张量精度""源事实""第四类键"中的任何一条 → **不要动 A 层**,
直接走 `QuantPlan` 既有值 + `KeyConvention` 既有三类键。

### B. 起点族(**新目录** `crates/models/src/formats/<fmt>/`)

| # | 模块 | 职责 | 判据/门 |
|---|---|---|---|
| B1 | `reader.rs` | 容器解析(header / 元数据 / 张量表 / 对齐 / mmap),**纯 host、零拷贝** | 与**独立第三源**逐字段对拍(GGUF = `gguf-py`:441/851 张量,名字·型·形状·偏移·字节数全等) |
| B2 | `meta.rs` | 超参 → `ModelSpec`(维度/层型表/tied/eps) | ① 与手写预设**逐字段**;② **超参↔张量形状互证**(不符=文件自相矛盾⇒拒);③ 层型表**以键面为权威**(GGUF 教训:4B 的 `block_count=33` 含 MTP 块,拿 interval 硬推会全判错) |
| B3 | `tokenizer.rs` | 内嵌词表 → `tokenizers::Tokenizer`(+ 特殊 id) | 与官方 tokenizer 工具**逐 token** 对拍;`decode` 往返无损 |
| B4 | `convention.rs` | `KeyConvention`:本地键 ↔ 文件键 | **I-7 键面集合相等**(声明键面 ≡ 索引键面,机器判据);未用键必须能归因(如"MTP 块") |
| B5 | `plan.rs` | `PlanTable`:逐键精度 → `QuantPlan` | 型直方图 × PORTED;★ **构造期一步判死**(缺键/未移植型/形状不符) |
| B6 | `transform.rs`(可选) | **写侧把语义烘进权重**时的读侧逆变换(逐键描述符) | 见 §三纪律 2;必须有**代价分层**表(哪些能字节级、哪些只能激活侧) |
| B7 | `source.rs` | `WeightSource`:键 → **字节**(不含设备/布局知识) | 压缩件**原样交付**(槽 dtype=`U8`,字节数 == 文件 `nbytes`)⇒ I-3 压缩驻留 |
| B8 | `dequant.rs`(可选) | CPU 参考解量化(金标) | 与独立实现**位级**对拍(GGUF:5 型 11 张量 `max|Δ| == 0`) |
| B9 | `*_gate.rs` | 设备链路对拍门(装得对 ≠ 算得对) | 见 §四 |

| # | 落点 | 触发条件 | GGUF 实证 |
|---|---|---|---|

### D. 内核族(`crates/kernels/`)

| # | 落点 | 内容 | 三条硬律 |

## 三、四条纪律(本轮的学费)

### 纪律 1:先问"这个格式**能不能**表达逐张量精度"

若格式允许混型(GGUF),**必须**走 `PlanSource::Keyed` + 构造期覆盖门;
若格式天然单精度(safetensors F16),直接 `QuantPlan` 值,别为"统一"而统一。

### 纪律 2:**转换器把语义烘进权重**时,先读转换器源码,再定代价分层

GGUF 的写侧(`llama.cpp/conversion/qwen.py`)对 qwen35 做了**六类变换**
(V-head 重排 / `A_log → -exp` / norm `+1` / conv1d V 段 / 合并键拆开 / out_proj 列重排)。
读侧每条都要逆,而**代价不同**:

| 粒度 | 例子 | 做法 | 运行期成本 |
|---|---|---|---|
| 行(外维) | alpha/beta/qkv-V/gate | 装载期**字节级**搬整行(行=内维完整块链) | **0** |
| 逐元素(F32 小件) | `ssm_a`(`ln(-x)`)、dt_bias、conv1d | 装载期 host 变换 | **0** |
| 列(内维) | `ssm_out` | **跨量化块** ⇒ 激活侧等价置换(**折进量化核**) | ≈0 |
| 逐元素(norm) | `attn_norm` 等 | **语义法**(`w_off=false`,零变换) | 0 |

**两条血泪**:
- **不要在 CPU 里硬解排列**(O(n²) python 逐行匹配跑到挂死)—— 读转换器源码才是权威;
- 用 2-3 个 F32 小张量做**廉价实证**交叉验证(我们就是这样把六类变换全部钉死的)。

### 纪律 3:**端到端必须有一条"一票否决"判据**

"输出看起来像话"**不是**判据:27B 首次运行的重复环垃圾
(`-pluginでは导师 Kitset-setsetset…`)**通过了**"字符种类 ≥ 4"的检查。
真正的判据是**首 token**(由整条预填充链决定)+ 与独立 oracle 的同文件贪心对拍。

**为什么量化档不能拿"逐 token 全序列"当硬门**:两条实现路径在 **near-tie** 处必然分叉
(实测 oracle 侧 top-2 间隔 **0.14 nat / 0.013 nat**,且两次分叉**各由不同一侧**命中 argmax)。
⇒ 判据 = **首 token 硬门 + 全序列软账 + 分叉点记 margin**。

### 纪律 4:生产白名单**生成,不手抄**

`awq27b` 档曾因白名单漏一条而整档起不来;新档的白名单必须按**发射账并集**生成:
`[cuda] trace_ring` 起机 → 打齐形状 → 每轮 `GET /debug/launches` 取 `cmd=="launch"`
的 `name` **取并集**(⚠️ ring 会绕圈,只 dump 一次实测漏 5 个解码臂)→ 入 `PROD_*` 台账
→ 由 `ops_whitelist.rs` 两处锁。**新 flavor 不加进那两个门 = 白名单没被审计。**

## 四点五、TP(可选但要想清楚的三件事)

| # | 问题 | 判据 | GGUF 的答案 |
|---|---|---|---|
| T1 | 通用 span 包装器够不够? | 切点在**块边界**上是不是一维连续区间 | 不够(块算术 × v-head 全局置换)⇒ `WeightSource::owns_shard()` 交由**源**交付本 rank 字节 |
| T2 | 目标坐标取什么? | 装载后的张量应等于**逆变换后**(语义序)张量的连续块 | grouped 序 ⇒ 每 rank 拿连续段,激活侧**不需要**任何置换表 |
| T3 | 分片档的源事实变不变? | 层的构造期事实是否依赖"权重是文件序" | 变:TP 档 `vhead_tiled_columns = false`(源侧聚合),虚拟置换键**响亮拒** |

**门的最小集**(零 GPU 的两条先跑,再上真机):① 几何手算钉值;② 几何自洽
(两 rank 交付量之和 == 全量);③ **逐键逐位**(分片读 == grouped 全量窗口);
④ 装载账(分片 spec × 计划表 × `elem_len` 三方一致);⑤ 双卡 e2e 首 token + 两 rank 一致。

## 五、反模式清单(每条都真实踩过)

| 反模式 | 后果 | 正解 |
|---|---|---|
| 在 CPU 里"硬解"排列/解量化 | O(n²) 挂死;且与内核算术漂移 | 读转换器源码;解量化只在核内 |
| 拿"字符种类/无重复"当连贯判据 | **静默错值放行**(27B 首跑) | **首 token 判据** |
| 白名单手抄 | 漏一条 ⇒ 整档起不来 | 发射账并集生成 + 两处锁 |
| 拿 `gguf_ty`(表是量化块)当 tied/untied 判据 | untied 模型把头算成 `hidden @ embᵀ`(**静默错值**) | 分支键 = `lm_head.is_none()`;**"表"与"头"正交** |
| 进程内绝对 `live` 账当单模型账 | 同进程 4B+27B 时假红(20.79 GiB) | 按**装载增量**算 |
| `CUDA_VISIBLE_DEVICES=<数字序>` | CUDA 序 ≠ nvidia-smi 序 ⇒ 用错卡(OOM/踩别人的卡) | **UUID 钉卡**(本仓纪律) |
| `pkill -f "<自己的命令行片段>"` | **自杀**(模式匹配到自身) | 按 PID kill |
| `/debug/launches` 只 dump 一次 | ring 绕圈 ⇒ 白名单缺臂 | 逐请求累积取并集 |
| 只跑一个靶位就宣称"格式通了" | tied/untied、单/双卡、K-quant/Q8_0 的**四象限只跑一半** | 至少两个形状不同的靶位 + 交叉源 |
